# NOVA 语义抽取原则

适用范围：`backend/app/services/ai/` 下一切把用户自然语言变成意图、业务字段或指代的逻辑，以及对应的提示词、Skill 和测试。

## 必须遵守

1. **意图与字段只由模型抽取。** 是否属于某业务、是新建还是修改、付款人/收款人、金额、AA 方式、备注、目标卡片、账户、对上一轮澄清的回答，都由模型输出到严格的 Pydantic Schema。
2. **禁止关键词/正则/句式模板做信息抽取或意图分流。** 不得新增 `re.search(r"加上|添加...")`、关键词集合、"X+动词+Y" 模板等去判断用户想做什么或提取字段；也不得用这类规则覆盖、改写或整体否决模型的结构化结果。发现某种说法没被理解时，修 Schema、上下文或提示词中的**通用语义说明**，不要把具体句子打补丁进正则或提示词。
3. **服务端只做核验，不做二次解析。** 允许的核验：
   - 引用核验：模型给出的 `*_quote` 必须逐字出现在可作为依据的用户原文中（子串包含检查，不是抽取）；
   - 引用解析：从服务端提供的候选列表（联系人、草稿卡、账户）中按 ID/精确名称核对；
   - 格式解析：把模型已摘出的金额片段交给 `nlu.amount_fen` 转成分；
   - 业务规则：权限、归属、版本、限额等。
4. **按字段降级，不整份回退。** 某个字段没通过核验，只丢弃该字段并告知用户“这一项未能确认”，不能丢掉其他已核验字段，更不能回退到规则解析器。
5. **执行结果必须如实反映。** 写入后按改动前后差异生成回复；没有实际变化时不得回复“已更新”，应说明哪些内容未能修改并请用户补充。
6. **模型不可用时不猜。** 离线或模型失败时，需要语义理解的业务直接说明需启用模型或请用户重试，不得用正则兜底。
7. **路由需要看到可续接的状态。** 追问能否续接，取决于路由与子模型能否看到当前未完成的草稿/任务摘要，而不是依赖关键词识别“这是追问”。

## 自查清单（提交前）

- 新代码里有没有对用户原文做 `re.search/re.match/in 关键词列表` 来决定意图或取值？有则改为 Schema 字段。
- 模型结果被丢弃时，是只丢了出错字段吗？
- 回复文案是否由实际写入差异生成？
- 测试是否以“模型返回某结构化结果”为输入（monkeypatch `llm.generate_structured`），而不是断言某正则能匹配某句子？
