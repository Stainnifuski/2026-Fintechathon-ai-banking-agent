# 收款申请 Skill（v2）

**收款**是当前登录用户向别人提出付款请求：钱将进入当前用户选择的本人银行卡。生成收款草稿或发出申请都不会从对方账户扣款；对方须另行接受、核对并按银行流程确认付款。

**转账**是当前登录用户主动从本人付款账户向别人付款，方向与收款相反，只能使用转账工具。“别人向我收款”是本人收到的付款请求，不等于我向别人发起收款。

1. 先调用 `inspect_collection_request`，由模型按语义理解本轮话语（结合未发出的草稿、本人联系人、本人账户和上一轮澄清问题），再调用 `manage_collection_request` 写入草稿。服务端不会用关键词或句式重新解析原话，只核验摘录片段出自用户原话、所选对象出自候选列表；某一项无法核验时只放弃这一项并告诉用户。
2. 付款对象可以是点名的人、本人已保存联系人全体，或尚未指定。“全体联系人”这类说法是范围，不是人名，不得生成添加联系人卡。只有明确点名的人才作为姓名或备注名，不凭联系人列表自行添加付款人。未说出的字段保持空白。
3. 只以当前用户已保存的联系人匹配付款人。唯一匹配时默认勾选；未匹配时显示姓名预填的添加联系人卡，手机号、银行卡号和备注名均留空；同名不唯一时让用户在卡片中选择。
4. 已有草稿时，用户后续的补充（新增或去掉某人、给出金额、改 AA 方式、改备注或收款账户、撤销）都是对该草稿的修改，哪怕只说了一个名字或一个数字；只有明确要另起一笔时才新建。指代已有人群的说法（如“每个人”）沿用草稿原付款人。没有可指代的人群时先澄清是哪一组人；用户回答澄清问题时，续接上一句需求并保留其中已说明的信息。
5. 多张草稿同时存在时，只依据用户明确的序号、原付款人等特征定位；不能唯一定位就询问。
6. 金额的“总额均分”与“每人各收”是两种方式：总额由所选付款人均分时预勾选 AA，否则按每人金额。
7. 收款账户默认本人第一张可收款银行卡，用户可以在对话或卡片中更换。不得把对方的银行卡当作本人的收款账户。
8. 联系人补全、金额、收款账户和参与人都由服务端重新验证。用户在卡片上点击“发出收款申请”后才调用银行批量收款申请接口；聊天文字不视为提交或对方付款授权。收款申请发出后只显示申请状态，不声称钱已到账；已发出的申请不能通过撤销草稿追回。
