## 实际发现及修复

1. 原运行库部分基金（如000015／000410）已有v3规则，初次尝试使用v3时被正确拒绝；差异是`rules.dataset_version`：既有`b498da40b510a409211716f0`，新缩减集不同。没有覆盖旧v3；改用v4并重新生成数据集、披露绑定、快照和资料包，增加已有v3的双库回归。
2. SQLite画像加锁使用同值UPDATE仍触发`updated_at`，导致严格保护检查拒绝。修正加锁UPDATE显式保留原更新时间；没有忽略字段或放松画像版本校验，增加已有画像原时间的保护回归。
3. 历史持仓赎回原来把买入批次版本当当前申赎版本，目录升级后可能拒绝。现在按历史持仓核对本人/可赎份额，用当前版本重新预览与授权；旧批次、成本、解锁日期和历史规则仍保留。SQLite/PostgreSQL相关赎回10项通过。
4. SQLite备份直接写Windows bind较慢。改为在数据库原生文件系统内完成SQLite backup，再顺序复制完整文件到持久备份目录。第一次慢备份未删除或截断，已完成保留。
5. 后端重建后，旧Nginx的健康/DNS状态可能导致Compose误判前端。启动器改为先构建、等后端升级健康，再单独重建前端；不强制重建PostgreSQL。
