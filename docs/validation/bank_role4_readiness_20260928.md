## 已复现的待修复问题

### 1. AA 批量申请并发重试产生 HTTP 500

- 位置：`backend/app/services/bank/payment_request_service.py`，`create_payment_request_batch` 的提交处；路由为 `POST /api/v1/payment-requests/batch`。
- 在隔离 PostgreSQL 库，用同一幂等键并发发出四个相同批量请求，参与者 U002/U003、每人5元。
- 服务级探针：一个请求抛出 `IntegrityError`，其余取得相同两条申请。
- HTTP探针：实得 **201、500、500、500**（调用顺序中的响应为500、201、500、500）。测试身份通过依赖覆盖设置为虚构 U001，银行服务与数据库使用真实实现。
- 原因：单人创建已有唯一冲突回读处理，批量创建在先查后插之间遇到并发时，没有相应的异常回读与稳定错误映射。
- 未观察到重复申请或扣款；问题是重试结果不符合幂等响应约定，并暴露为服务器错误。
- 修复验收应证明：同键同参全部回读同一批申请；异参返回明确409；不产生半批和额外记录。

### 2. 订阅扣费对异常历史金额静默舍入

- 位置：`backend/app/services/bank/subscription_service.py:158`，`round(account.balance * 100)`。
- 隔离库将账户历史余额设为 **100.001元**，调用现有15元订阅扣费。
- 实得扣费成功、余额 **85.00元**，并未像转账服务一样拒绝非法的分精度。
- 当前运行库没有发现这种异常余额；这是历史数据损坏情况下的银行金额校验缺口。
- 修复验收应证明：辅助扣费统一使用严格金额转换，异常金额返回稳定业务错误，余额/流水/订阅日期均不改变。

以上属于4号银行包的现有服务正确性问题。它们尚未修复，不包含在此前94项测试的成功结论中。

## 接口准备情况

现有说明：`docs/contracts/转账任务状态机_API_v0.1.md`（内容标题v0.4）、`docs/bank/手机号转账与风险边界.md`。实际 OpenAPI 和交互文档可从运行后端读取：

- `http://localhost:8000/openapi.json`
- `http://localhost:8000/docs`

5号已有 `BankApi` Protocol 和 `HttpBankApiClient`，不直接访问银行ORM或复用银行数据库会话；边界测试通过。

| 方法 | 银行内部路径 | 当前能力 |
| --- | --- | --- |
| POST | `/api/v1/internal/bank/transfers/directory` | 按姓名/手机号取得脱敏付款与收款账户候选 |
| POST | `/api/v1/internal/bank/transfers/validate` | 归属与状态校验、用户级业务日转出事实 |
| POST | `/api/v1/internal/bank/transfers/resolve` | 唯一姓名解析，歧义拒绝 |
| POST | `/api/v1/internal/bank/operations` | 整数分命令、可信执行上下文、幂等记账 |
| GET | `/api/v1/internal/bank/operations/{operation_id}` | 银行业务结果查询 |
| POST | `/api/v1/internal/bank/payment-requests/{operation_id}/release` | 释放未提交收款申请占用 |
| POST | `/api/v1/internal/bank/totp/verify` | 银行身份数据上的验证码核验，授权策略由3号负责 |

内部入口使用服务端独立 `X-Internal-Token`；浏览器不能持有它。用户端查询接口有JWT和账户归属检查，实际读取边界验证通过。

### 冻结前需补齐的银行契约内容

1. **完整响应DTO**：目录、手机号候选、收款人列表、TOTP响应仍为宽泛的 `dict/list[dict]`，OpenAPI没有列出完整字段及可空性。内部结果 `status` 仍是一般字符串，需明确银行枚举与当前实际返回状态。
2. **逐接口字段和样例**：提交、查询、目录、释放至少各给出一份完整请求/响应及异常样例；说明谁生成编号、摘要格式、金额单位、时区、主体身份来源、执行上下文责任。
3. **统一错误契约**：业务错误多数已有 `detail.code/message`，但鉴权等路径仍有字符串detail，422校验又是框架数组格式；AA并发还会500。需要写清调用方如何分类处理，不能声称所有错误都已统一。
4. **超时与查询语义**：HTTP适配器当前超时10秒；5xx/网络异常视为未知。规范中应集中列出：复用原 operation_id、先查询、不得改号重付、404未找到不能独自证明以后不会执行。还应区分首个失败响应与同号回读 `FAILED` 的HTTP/业务结果。
5. **版本与协作签认**：文档顶层v0.4、后段v0.3以及旧文件名需要明确版本策略；4号提交银行章节，5号负责共享契约统稿和组织调用方确认。

这属于“入口和主要语义已准备好，可开始联调”，尚不是“每项已完整文档化、由团队冻结”。
