# 统一3000入口：部署修复与验证（2026-10-16，多伦多）

## 原因和范围

本机原有3000旧镜像、3010旧dist挂载、3014源码Vite三套前端；并非同一端口争用。旧Docker后端使用另一套PostgreSQL，3014使用独立SQLite账本。Git更新不重建镜像，因此队友使用3000仍可能看到旧版本。

本轮保留现有理财即时申赎等源码成果，将唯一正式入口固定为`http://localhost:3000/`。Nginx同源代理`/api/`、`/health`、`/docs`、`/redoc`、`/openapi.json`；银行8000仅在Docker内部，不再发布宿主端口。Vite也固定3000和strictPort，与Docker前端互斥。共用银行API及原号恢复接口保留；历史测试服务器的`joint-test`入口不进入正常应用。

Backend镜像以仓库根目录为构建上下文，包含backend、公开config及运行CLI；AKShare1.19.1可用。固定快照独立只读挂载，不把运行库、密钥或全量缓存烘入镜像。Frontend在Linux构建中补齐其DEV组件类型检查所需的公开JSON fixture，正式应用仍由Vite剔除DEV预览。

`start_bank.cmd`/`scripts/start_bank.ps1`校验配置与资料，重建前后端，等待理财就绪，并核对运行source_revision。源码ZIP没有Git时使用source-archive标识，不要求安装Git才能启动。正常默认仍使用PostgreSQL；本机私有覆盖显式选择已确认的SQLite账本。

## 数据与安全边界

用户选择沿用原3014账本，旧PostgreSQL备份保留且不合并。停止旧写入后，通过SQLite backup API制作副本并逐表核对，随后转入Docker本地`bank_runtime_data`卷。首次Windows bind目录下读库约54秒，内部30秒读取超时；采用Docker原生卷后同一完整目录首次读取5.951秒。没有缩池、改风险、重采集或重写缓存架构，也没有改财务算法。

Docker卷切换后与冻结源副本10表的行数及内容SHA256均一致：用户8、账户15、订单13、持仓批次5、现金占用10、份额占用2、流水8、结算10、评估13、context9。核对包含既有记录全文；验证推荐/Plan/prepare没有新订单或占款。正常后台仍按原规则处理历史已授权在途，未把历史订单改造成新的即时成交；原3014源库及旧PostgreSQL未被合并或清空。

本机现有非标准用户ID账本通过`BANK_SEED_DEMO_DATA=false`避免注入手机号冲突种子。显式SQLite本地测试模式保留用户此前已要求的问卷次数设置；正常模式仍2/8，风险等级、确认及MFA不放宽。正常应用使用真实当前时钟，没有移植冻结全局测试时钟。模型仍沿用本机原离线测试模式；未将这次检查称为真实LLM联调。

私有运行配置、JWT/内部令牌、账本和备份仅存本地`.deps`，不提交。旧容器元数据中可能有私有环境，仅保存在忽略目录，不输出到文档。原工作区已有未提交成果及其.env未覆盖。
