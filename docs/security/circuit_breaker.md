# 异常熔断与安全锁定（2026-10-22）

## 范围和默认规则

服务端统一判定，状态持久化在 `security_states`，与客户停用及银行卡状态分离。安全时间使用真实UTC；理财业务时钟和浏览器时间不参与锁定判定。

| 分类 | 窗口、阈值 | 结果 |
|---|---|---|
| 登录错误 | 10分钟内连续5次；成功登录重新开始本类计数 | 限制同一规范手机号的登录15分钟；未知号码执行相同规则和响应 |
| 交易强验证错误 | 10分钟内连续5次，或窗口累计10次 | 用户交易锁15分钟；短信/TOTP、转账/卡片/理财共用预算 |
| 明确授权违规 | 5分钟内3次 | 用户交易锁30分钟 |
| 明确提示注入 | 同一用户同一会话5分钟内3次 | 暂停该Agent会话5分钟；单次先拒绝本请求 |
| Agent工具失败 | 单轮连续3次错误；原有同参数第三次重复规则保留 | 停止本轮，不锁用户交易 |

仅 `TOTP_INVALID/TOTP_REPLAY/SMS_INVALID` 计入交易验证失败。成功强验证清除连续次数，保留窗口累计数；其他查询、登录成功不清除交易计数。重新发码、改验证方法、换任务和新会话都不清除用户交易计数。每次实际提交的错误证明均计数，不能通过复用客户端request_id豁免。

明确授权违规当前接入转账服务的 `PAYER_FORBIDDEN/EXECUTION_CONTEXT_INVALID/PARAM_DIGEST_MISMATCH`，以及卡片本人确认摘要的 `DIGEST_MISMATCH`。身份来自认证上下文。404、过期、业务版本变化、余额不足、取消、网络及模型故障均不计为用户违规。注入检测是启发式信号，只暂停会话，不据此冻结用户。

## 服务和事务边界

- `check_trade()`：编排及页面入口的只读早期检查。不可持安全行锁再调用独立HTTP银行事务，避免跨请求互等。
- `require_trade()`：银行最终受理的安全行锁，直至账务事务提交。PostgreSQL使用冲突安全插入及行锁；SQLite使用写操作取得跨连接写锁。
- 失败验证先回滚调用方全部未提交业务，再原子提交公共计数、安全审计及必要的短信单条尝试数。没有内层独立连接等待外层持锁，也不为保存次数提交待执行账务。
- 成功验证的防重放证据和连续次数重置随成功事务提交。
- 安全触发时提升 `generation`，记录 `revoked_before`。已签发且尚未受理的授权按签发时间失效。交易计数达到阈值的本次响应即为429锁定，不再等下一次尝试。
- 锁定期间的额外请求不会持续延长截止时间。冷却结束后可新建授权；旧授权不恢复。到期恢复在下一次持锁事务中惰性记录一次审计。
- 安全审计记录分类、规则码、次数和版本，不记录验证码、密码、手机号或聊天原文。登录计数主键以服务端密钥HMAC手机号，不存明文号码。

## 覆盖入口和允许操作

最终银行拦截覆盖转账、普通/快赎及整份理财受理、增加风险的卡片变更、模拟用卡交易和模拟订阅扣费。转账内部HTTP与定时调度共用门禁，不依赖前端按钮或Agent是否遵守提示。

锁定期间仍可读本人账户、流水和原操作结果；允许取消待执行任务、取消订阅和本人主动锁卡（`card_lock`，仍需本人确认）。保护白名单固定在服务端，其他卡片操作不自动加入。

定时转账被阻断后记录任务 `error_code`，调度器不自动恢复；用户可取消或修改生成新的授权。任务查询隐藏当前不可用的确认/验证/执行动作并显示安全原因。卡片单笔失败上限仍终止该笔操作；公共用户锁优先返回。

既有银行事实先按原号回读；成功重复提交不因新锁而变成失败，未知提交继续按原号核对，已受理理财照常结算。转账outbox遇到明确的安全拒绝，不再创建可能在解锁后执行的重试。

## 接口

`GET /api/v1/auth/security/status` 需要登录，只返回本人当前有效锁：

```json
{"locks":[{"scope":"trade","reason_code":"TOTP_INVALID","locked_until":"2026-10-22T08:15:00+00:00","retry_after":900,"generation":1}],"trade_locked":true,"message":"查询、取消待执行任务和保护操作仍可使用；旧交易需重新确认验证。"}
```

登录锁：429 `LOGIN_LOCKED`；用户交易锁：429 `SECURITY_LOCKED`；旧授权：409 `SECURITY_RECONFIRM_REQUIRED`。能直接传递安全异常的接口另带 `scope/reason_code/locked_until/retry_after/generation` 以及 `Retry-After`；部分原有编排适配器只保留code/message，页面可通过状态接口补齐。Agent会话暂停通过聊天的 `grounding.status=blocked/reason_codes=[AGENT_SESSION_LOCKED]` 返回，支持普通与流式聊天。

内部转账可信上下文新增可空 `authorization_issued_at`（带时区ISO时间），由任务服务从服务端授权行填写。无锁定历史的旧内部客户端保持兼容；用户发生过交易锁后，缺少时间或时间早于失效边界的旧客户端不能提交新账务。该字段只在独立内部令牌保护的接口接受，不属于浏览器授权证据。

前端每30秒及收到安全拒绝时刷新状态，显示原因和预计恢复时间；公共验证码组件清空当前因素并禁用发码/切换。验证失败不清除登录令牌。解锁仅恢复发起新操作的能力，不自动提交旧交易。

## 配置、增量升级和运行

全部参数见根目录 `.env.example` 的 `SECURITY_*` 区域，取正整数。默认10分钟验证窗口、5次连续/10次累计、15分钟交易锁；登录独立15分钟锁；违规30分钟锁；会话5分钟锁。

重启新版后端时，现有 `init_db()/Base.metadata.create_all()` 增量创建新表和用户索引；不重建银行表、不修改余额、不重置种子数据。重复启动不清空计数。不要让旧版本继续接收交易，因为旧版本不认识安全门禁。恢复旧版本不能作为正常解锁方式；无需删除新表。首版采用冷却恢复，不提供普通JWT或Agent可调用的提前解锁接口。

验证记录见[本轮验收](../validation/security_circuit_breaker_20261022.md)。PostgreSQL并发用例需要显式配置隔离的 `BANK_TEST_DATABASE_URL`，普通回归不使用业务库。
