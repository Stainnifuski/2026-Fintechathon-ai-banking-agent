# 4号模拟银行接口与数据库交接 v0.5

范围：模拟客户、账户、手机号目录、余额、流水、转账记账、收款申请、订阅及银行事实审计。3号负责授权与风控，5号负责计划、确认、调度和恢复，2号负责理解，1号负责页面。其他模块通过接口访问银行，不直接查询或更新银行表。

## 契约入口与兼容性

- 运行后访问 `http://localhost:8000/docs`；机器可读定义为 `/openapi.json`，包含必填字段、可空类型、长度、枚举和错误模型。请求及响应以运行版本生成的 OpenAPI 为准。
- 浏览器接口使用 `Authorization: Bearer <access_token>`；内部银行接口使用独立 `X-Internal-Token`，该凭据不得进入前端。缺失配置返回503，错误内部凭据返回403。
- 本次保留公开接口的元单位：账户 `balance/daily_transfer_used/daily_transfer_limit`、流水 `amount`、收款申请输入 `amount`、订阅展示 `amount/charged_amount` 都是元。所有 `*_fen` 均为整数分，禁止再乘/除100两次。
- **数据库结构改变**：账户金额与流水金额改为 BIGINT 分，旧 SQL `accounts.balance`、`transactions.amount` 必须更新。ORM实例元属性为兼容属性，不再是可用于 SQL 查询的映射列。其他成员应通过 HTTP 而非依赖这些 ORM。
- 错误统一为 `{"detail":{"code":"VALIDATION_ERROR","message":"请求参数无效","issues":[]}}`。422的 `issues` 为 `{loc:["body","字段"],type:"…",message:"…"}` 数组，不回显输入值。原先读取字符串 `detail` 或 FastAPI 默认错误数组的客户端需改为读取 `detail.message`。

## 银行内部接口

前缀 `/api/v1/internal/bank`；所有请求需要内部凭据。除明确标注外，成功为200。

| 方法与路径 | JSON请求或路径参数 | 成功响应 |
|---|---|---|
| POST `/transfers/directory` | `subject_user_id`，至少提供 `recipient_name` 或 `recipient_phone`；同时提供时必须指向同一客户 | `{payers:[{account_id,label}],default_payer:string或null,recipients:[{account_id,label,recipient_user_id,phone_masked}]}` |
| POST `/transfers/validate` | `subject_user_id,from_account,to_account`，可选 `recipient_phone` | `{from_account,to_account,recipient_name,daily_transfer_used_fen}` |
| POST `/transfers/resolve` | `subject_user_id,recipient_name` | 校验响应另含 `recipient_user_id`；姓名不唯一不猜测 |
| POST `/operations` | 见下方命令 | `{operation_id,status,bank_tx_id,error_code}` |
| GET `/operations/{operation_id}` | 原业务编号 | 同上；尚无记录返回404 `NOT_FOUND` |
| POST `/payment-requests/{operation_id}/release` | `{subject_user_id}` | 204，无响应体；释放尚未记账的申请占用，不能撤销已成功记账 |
| POST `/totp/verify` | `{subject_user_id,proof}`，proof为6字符验证码 | `{verified:true}`；沿用现有TOTP防重放规则 |

提交命令示例（`param_digest` 必须按下述算法计算）：

```json
{
  "operation_id": "demo-operation-0001",
  "from_account": "A001",
  "to_account": "A003",
  "amount_fen": 1234,
  "currency": "CNY",
  "param_digest": "由下面算法生成的64字符SHA256摘要",
  "note": null,
  "recipient_phone": "13900000002",
  "subject_user_id": "U001",
  "authorization_id": "由3号和5号提供的授权编号",
  "control_epoch": 1,
  "simulate_response_loss": false
}
```

`operation_id` 长8–64；金额为正整数分，最大2,000,000,000分，仅支持CNY。`control_epoch >= 1`。备注为空时传 `null`；非空最多256字符，不允许控制字符。服务不自动填“转账”。手机号是可选的再次核对条件，不替代收款账户。

Python摘要算法与银行一致；手机号先使用共享 `normalize_phone` 规范化，缺省手机号不加入摘要：

```python
import hashlib, json
from backend.app.domain.phone import normalize_phone

payload = dict(from_account="A001", to_account="A003", amount_fen=1234,
               currency="CNY", note="")  # note为null时摘要取空字符串
payload["recipient_phone"] = normalize_phone("13900000002")
digest = hashlib.sha256(json.dumps(payload, ensure_ascii=False, sort_keys=True).encode()).hexdigest()
```

正常成功响应示例：

```json
{"operation_id":"demo-operation-0001","status":"SUCCEEDED","bank_tx_id":"BTX...","error_code":null}
```

当前银行同步处理，持久化终态为 `SUCCEEDED/FAILED`；OpenAPI的共享状态枚举还保留其他状态用于协议扩展。只有 `SUCCEEDED` 和有效 `bank_tx_id` 表示成功。首次余额不足/日限额拒绝返回400，持久化为FAILED；原号重试或查询返回该FAILED事实。验证阶段拒绝可能没有银行操作记录。

同号同参返回同一结果，异参409 `IDEMPOTENCY_CONFLICT`。原号不可用于第二笔业务。HTTP客户端超时10秒；超时、网络中断、5xx、故障注入504 `BANK_RESPONSE_LOST` 都不能推定未扣款。5号保留UNKNOWN，按原号查询；404只表示查询时未找到，不能据此换号重发。若需要重试提交，只能复用原编号、完整参数与可信执行上下文。查询本身不转账。

常用错误码：400 `INSUFFICIENT_FUNDS/DAILY_LIMIT_EXCEEDED/SAME_ACCOUNT`；403 `PAYER_FORBIDDEN/ACCOUNT_INACTIVE/EXECUTION_CONTEXT_INVALID`（具体领域码以响应为准）；409 `IDEMPOTENCY_CONFLICT/PARAM_DIGEST_MISMATCH/PHONE_CONFLICT/RECIPIENT_MISMATCH/BANK_INTEGRITY_CONFLICT`；422 `VALIDATION_ERROR/INVALID_AMOUNT/INVALID_CURRENCY/INVALID_PHONE/INVALID_NOTE`；503 `BANK_BUSY/BANK_LEDGER_INVALID/INTERNAL_BANK_TOKEN_MISSING`。业务错误响应不代表所有情况都存在银行操作，恢复须结合查询结果。

## 用户接口

| 接口 | 输入/用途 | 响应 |
|---|---|---|
| POST `/api/v1/auth/register` | `name,phone,password`；可选risk_level | TokenSchema，注册自动生成账户 |
| POST `/api/v1/auth/login` | `phone,password` | `{access_token,token_type,user}` |
| GET `/api/v1/auth/me` | 当前登录用户 | UserSchema |
| GET `/api/v1/accounts/{user_id}/accounts`、`/balance` | 只能读当前用户 | AccountSchema[] / AccountBalanceSchema[] |
| GET `/api/v1/transactions/history` | 本人流水，limit为1–500，默认50 | TransactionSchema[] |
| GET `/api/v1/transactions/{tx_id}` | 本人流水明细 | TransactionSchema |
| GET `/api/v1/users/recipients` | 活跃模拟收款人 | `{user_id,name,phone,account_id,bank}[]`，phone脱敏 |
| POST `/api/v1/users/recipients/phone` | `{phone}` | `{account_id,label}[]`，只返回脱敏候选 |
| POST `/api/v1/payment-requests` | `payer_user_id,receive_account_id,amount,idempotency_key`，可选note | 201 PaymentRequestView |
| POST `/api/v1/payment-requests/batch` | `payer_user_ids,receive_account_id,amount,idempotency_key`；可选note、split_equally | 201 PaymentRequestView[] |
| GET `/api/v1/payment-requests` | role=all/incoming/outgoing | 当前用户参与的PaymentRequestView[] |
| POST `/api/v1/payment-requests/{id}/accept` | `state_version,payer_account_id` | TaskSnapshot待确认计划；不直接扣款 |
| POST `/api/v1/payment-requests/{id}/reject`、`/cancel` | `state_version` | PaymentRequestView |
| GET `/api/v1/subscriptions` | 本人订阅 | SubscriptionView[] |
| POST `/api/v1/subscriptions/{id}/cancel` | `state_version` | SubscriptionView |
| POST `/api/v1/subscriptions/{id}/simulate-charge` | `state_version,idempotency_key` | `{subscription,transaction_id,charged_amount,duplicate,message}` |

收款申请响应包含：`payment_request_id,requester_user_id,requester_name,payer_user_id,payer_name,receive_account_id,amount,amount_fen,currency,note,status,state_version,expires_at,created_at,responded_at`。状态为PENDING/ACCEPTED/PAID/REJECTED/CANCELLED/EXPIRED；操作携带当前版本，旧版本409。批次最多20人，不能重复或包含本人；金额最多100万元且必须精确到分。`split_equally=true`时amount为总额，不能整分均分则拒绝整批；false时为每人金额。

批次以申请人+根幂等键绑定参与人集合、金额、均分方式、收款账户和备注。四个并发同键请求回读相同申请，异参409，不生成半批。v0.5之前的批次没有根记录，首次重放按已有子记录核对并补登记；无法完整复原旧批次的原始参与人集合，因此升级前已创建的旧批次不要修改参与人后复用根键。

订阅响应包含 `subscription_id,debit_account_id,debit_account_label,merchant_name,amount,amount_fen,currency,billing_cycle,next_charge_at,status,state_version,source_transaction_id,cancelled_at`。模拟扣费是真实修改**模拟账本**，同编号重试只扣一次；取消后禁止新扣费。此接口用于演示，不连接真实支付渠道。

## 数据库升级与回退

1. 停止旧后端写入并备份数据库。不得删除Docker数据卷或重新seed来替代升级。
2. 启动新版后端：初始化自动创建新表、迁移金额列、补齐MFA/手机号登记；之后seed仅补缺失演示数据，不重置余额。
3. 金额迁移会先验证全部账户与流水。负数、非有限值、超出分精度、零金额流水、混合结构或越界会中止；不静默舍入。PostgreSQL迁移期间锁住两表，DDL与数据变更在同一事务中完成。需要预留停服窗口。
4. 核对升级前后每账户余额、日额度、流水金额和条数；保留备份至验收完成。

迁移结果：`accounts.balance_fen/daily_transfer_used_fen/daily_transfer_limit_fen`、`transactions.amount_fen` 为BIGINT；新增 `payment_request_batches` 保存批次摘要。应用层严格检查整数分；数据库约束禁止负余额和非正流水。金额上限为BIGINT范围，业务转账另有更低上限。

如需回退，先停止后端，用**新版代码**连接同一数据库执行：

```sh
# 从仓库根目录运行；DATABASE_URL需指向目标库
python -m backend.app.services.bank.migrate --rollback-money
# Docker镜像内包名是app
docker compose run --rm --no-deps backend python -m app.services.bank.migrate --rollback-money
```

成功后再启动旧后端。回退从当前分余额转换元，不丢弃迁移之后的新流水；如旧浮点结构不能精确表示当前金额会拒绝回退，保留新结构，需人工处理。新批次/审计表可保留，旧代码不使用。前进命令去掉 `--rollback-money`。迁移不提供滚动混跑支持，不能让旧代码连接新金额列。

## 审计和验收边界

银行转账成功及持久化失败、收款申请创建/接受/拒绝/取消/释放、订阅取消/扣费均与银行状态在同一事务写 `audit_logs`；审计写失败不允许账本单独提交。重复成功请求不追加重复事实。参数只含业务编号、整数金额、摘要、授权关联等，不复制手机号、备注、密码或验证码。

银行日志标记 `intent=bank_business,permission_level=delegated,user_confirmed=null`；仅证明银行执行事实，3/5号应按operation_id/authorization_id关联用户确认、风控等级与授权记录。预校验拒绝与到期读取不保证各有独立业务审计行；现有HTTP日志也不能替代3号安全审计。不能据此宣称全系统生产合规已完成。

执行 `pytest tests -q` 覆盖本地SQLite；设置 `BANK_TEST_DATABASE_URL` 可额外执行真实PostgreSQL验收，数据库名必须以 `bank_test_` 开头。每例创建独立随机schema并清理，禁止指向业务库。验收报告见同目录及 `docs/validation`。定时调度、红色风险授权、独立worker等跨组能力仍按各自主责联合验收。
