# 账单决策与优化 v4（2026-10-19）

本次在[五项数据基础 v3](账单数据基础_API_v3.md)上完成分类、预算、异常核对，以及商户、退款、周期、预测和增量同步的优化。所有金额为整数人民币分，身份来自JWT；原始流水金额、类型、备注和分类保留，修正与用户决策写入独立表。

## 分类、预算和异常核对

- 分类支持餐饮、购物、交通、娱乐、订阅、学习、其他。商户关键词以及本人同商户的历史修正提供可解释建议，建议不会自行改动流水。本人可采纳单笔建议，或明确选择“同商户其他及未来消费沿用”。生效顺序为单笔修正、本人商户规则、原始分类。单笔与规则可分别撤销，退款跟随原单的有效分类；报告、下钻、消费变化、现金流消费基线与NOVA使用相同口径。
- 预算按月份、账户范围和分类保存，支持总预算、分类预算、启用状态及预警比例。转账与理财不占消费预算；到账退款抵减当期净消费，净额为负时预算占用按0计。当前月预测结合已知周期支出与有样本依据的可变消费，样本不足时明确标为“仅已知部分”。不同预算各自核对，不叠加总预算与分类预算；提醒只在应用内展示。
- 异常可以标记待处理、已核实正常、已解决并保存备注。已核对记录默认折叠，报告只提醒尚待核对的数量。依据指纹变化后重新进入待核对状态，旧核对事件仍留审计记录。不能通过伪造异常ID或金额绕过当前本人报告的依据校验。

| 方法 | `/api/v1/bills` 下的路径 | 写入约束 |
| --- | --- | --- |
| PUT | `/transactions/{tx_id}/classification` | `category`（null撤销单笔）、`apply_to_merchant`、`expected_version`、`expected_rule_version`；仅消费流水支持手动分类 |
| GET / DELETE | `/category-rules` / `/category-rules/{merchant_id}` | 删除需`expected_version`，规则归属本人 |
| GET / PUT | `/budgets?month=YYYY-MM` / `/budgets` | 月份、可空账户及分类、正整数`amount_fen`、`warning_percent`、`active`、`expected_version` |
| PUT | `/anomaly-reviews` | 当前报告`query`、`as_of`、`anomaly_id`、`fingerprint`、`status`、`note`、`expected_version` |

分类结果附带`raw_category`、`effective_category`、`category_source`、两个版本和建议依据。重复或过期的实际修改返回409，不静默覆盖另一会话的编辑。

## 商户预览、撤销与拆分

- 归并前GET `/merchants/{target}/merge-preview?source_merchant_id=…`，返回将移动的流水、别名数量和影响说明。POST `/merchants/{target}/merge`必须提交该次`preview_digest`；流水、别名或规则版本变化后需重新预览。不同已核实银行身份不得归并。
- GET `/merchant-history`查看变更记录；POST `/merchant-history/{event_id}/undo`撤销有完整还原快照的归并，恢复原来的别名、流水归属及识别周期偏好。归并后范围或规则改变时拒绝自动撤销，改用明确选择流水的拆分；历史v3缺少还原快照的归并保留记录，但不能伪造还原。
- POST `/merchants/{merchant_id}/split-preview`接收新名称、`tx_ids`和可选移动别名，列出连带的原单／退款家族及准确移动数量。POST `/merchants/{merchant_id}/split`附上同一组参数和`preview_digest`确认，参数和范围都参与校验。已核实银行付款身份的流水不能拆成不同身份；缺少该证据的历史记录可由本人明确拆分。新名称会登记为别名，使未来同名流水继续沿用新商户标识。名称已被其他商户使用则要求先明确处理别名归属。

## 多次部分退款

原花店／蛋糕店的`POST /merchant/orders/{order_id}/refund`新增可选`amount_fen`和`operation_id`。商户页面输入本次金额、核对原付款／累计已退／剩余可退后确认；同一次请求重试保留同一操作号。旧调用省略金额仍退回剩余金额，已完成的原整笔退款保持原幂等行为。

银行为每次退款写入独立双边流水和`merchant_refund_parts`事实，锁定原付款及账户，在同一事务内检查累计额度、商户余额、权限和幂等参数。累计不得超过原付款；同一操作号改金额会冲突，其他商户不能通过重放操作号读取或退款。并发的旧剩余额度请求最多一个成功，其余要求重新核对。全部退完才保存兼容的整笔完成标记，不与分次事实重复计数。

店铺状态新增`PARTIALLY_REFUNDED`；订单、商户统计和NOVA均显示累计金额。顾客账单原单显示`refunded_fen`、`refundable_fen`及全部关联退款ID。跨期和多次退款依然按各自到账账期计入，保留原单消费原额。

## 周期与现金流

识别与手动计划支持`WEEKLY`、`MONTHLY`、`QUARTERLY`、`YEARLY`。识别至少需要3笔稳定记录：周期间隔6–8天，其他频率按连续日历周期且日期差不超过3天或均为月末；金额跨度不超过中位数20%。识别组保留观察ID、频率和说明，不满足或过期的模式失效。银行订阅仍以原订阅计划为准。

POST `/recurring/plans`手动建立，PUT `/recurring/plans/{stream_id}`编辑。字段包含名称、本人有效储蓄账户、方向、频率、金额、带时区的首次日期、月末选项、分类、启用与有效状态、版本。日期始终从原始锚点推演，避免1月31日经2月后漂移；周计划不接受月末选项。手动计划不会执行扣款。相同账户商户同方向的启用模式不重复预测，建立手动计划会停用对应的历史候选；银行订阅取消仍走原确认流程。

`CashflowScenario`增加`one_off_events`（时间、用途、非零整数分金额）。必须在当前预测范围内；这些是假设，只影响情景线，不改变基准、仅计划线或账户余额。事件来源增加`recurring_plan`和`scenario`。消费基线使用有效分类，已识别或明确声明的固定支出从可变消费样本中剔除。

POST `/forecasts`保存无削减、无排除、无临时收支的基准预测，GET `/forecasts`查看预测与实际的收支净变化。快照固定账户范围、起止时间、预期金额和固定支出匹配证据；未来实际只读对应时间范围内的已完成流水，不能拿当前余额冒充过去期末余额。未到结束时间不计算最终偏差，授权范围变化时停止直接比较。

至少3个互不重叠、已结束且每期至少5笔实际可变消费的预测期才启用校准。最多取近期5个独立期间，将实际／原始预计可变支出比例限制在0.5–1.5，仅调整可变消费基线，避免反复乘上已校准的系数。返回`calibration`说明依据、系数和样本；不足时系数为1，不补造准确性。

## 同步、迁移和并发

- 采用新增辅助表，已有库不重建原始流水。账单查询索引通过银行迁移服务幂等补建。
- 升级到revision 4时仅做一次完整回填；后续启动只补缺失元数据并处理过期状态。转账、卡片消费、订阅和退款写入传递已知流水ID，只处理新增／受影响的流水和相应商户的有限历史。手动“刷新历史关联”保留完整修复能力。
- 专用用户锁按固定顺序取得；分类、预算、异常和周期编辑校验版本；退款另锁付款和账户。所有相关金融写入保持同事务，失败一起回滚。图表使用同步初始化及明确销毁，尺寸观察器在卸载时清理，避免快速切换后访问已销毁实例。
- PostgreSQL验收用`BILL_TEST_DATABASE_URL=postgresql+asyncpg://… pytest tests/integration/test_bill_postgres.py`。用例只创建随机命名的临时schema，并在结束时移除该schema，不清理现有业务表。当前环境没有运行中的PostgreSQL或Docker服务，实际并发已在文件型SQLite验证，PostgreSQL用例跳过。

NOVA新增只读`get_budget_status`、`list_forecast_reviews`，周期工具覆盖全部频率，情景工具接收临时假设。没有向模型开放分类、预算、异常修改、退款、归并确认或资金执行工具。
