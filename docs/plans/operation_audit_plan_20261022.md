# 操作审计实施方案（已确认，自审修订版）

日期：2026-10-22。用户已确认按本方案实施；实现说明见 `docs/security/operation_audit.md`，测试及实际边界见验收记录。

## 1. 目标和完成标准

对每项关键操作，能够回答：谁在何时通过哪个入口提出什么请求；系统依据什么事实和规则形成哪个版本的计划；谁确认、如何验证；调用了哪些工具和银行接口；哪些步骤真正提交；失败、阻断、取消、重试、人工接管和结果核对如何发生。

决策链路采用可核验的结构化记录：输入来源、结构化意图、计划及依赖、规则编号与版本、实际检查结果、授权证据引用、执行回执、答案依据引用。模型提供的计划与解释标明来源；确认、MFA和成交结论由对应可信模块提供。保存必要的理由摘要和证据引用，避免复制整段提示词、内部推理文本或完整账户查询结果。

最终交付包含统一事件存储、所有在范围内的业务接入、查询接口、本人审计页面、迁移、故障与隔离测试、覆盖矩阵和验收记录。下面的实施阶段是同一功能的交付顺序，全部完成才声明功能完成。

## 4. 存储与关联设计

保留旧 `audit_logs`、转账状态事件及其动作名、幂等逻辑、查询和风控统计。新增 `audit_events` 作为结构化审计明细，并新增轻量 `audit_event_objects` 关联表，支持一轮请求产生多笔任务/订单及跨请求追踪。

核心事件字段：

- 标识：`event_id`、`schema_version`、`event_type`、`source_module`、旧审计/状态事件引用。
- 请求：服务端生成的 `request_id`、`trace_id`、`span_id`、`parent_span_id`；另存业务幂等键 `business_request_id`，二者不混用。
- 身份：经过认证的操作者 `actor_type/actor_id`、数据归属 `subject_user_id`；后台任务记录系统执行者与被授权用户，未认证失败事件允许无用户归属。
- 业务：关联表记录领域、对象类型、对象ID、版本；覆盖会话、任务、计划、步骤、操作、授权、批次、订单、流水等，一条事件可关联多个对象。
- 决策：阶段、参数白名单摘要/现有参数摘要引用、输入来源引用、规则ID与版本、已核验事实、权限要求、确认/MFA结果、决策理由码。
- 执行：业务结果、HTTP/工具结果、错误码、尝试次数、脱敏前后差异、银行操作号/回执引用。
- 时间：UTC发生时间、记录时间、步骤序号、单调时钟计算的耗时；页面转换为北京时间。

`trace_id` 表示一次入口执行（HTTP请求或一次后台执行），同一次可信内部调用延续该trace并创建子span。后续确认、MFA、重试各有自己的trace，通过稳定业务对象关联成完整生命周期。同一会话可包含多项任务，一轮多任务共享请求关联而保留各自操作轨迹。

索引围绕“归属用户+时间/动作/结果”“trace+步骤”“领域+对象类型+对象ID+版本”建立。对象引用不使用会随业务删除的级联外键。因果顺序由父子span、计划依赖和对象版本表达，时间排序仅用于展示并行事件。

历史记录通过只读适配器展示原有事实，并标明 `legacy` 和“历史链路不完整”。不为历史交易推造意图、确认或MFA记录。新旧事件用来源引用去重；如将来需要回填，另用可重复运行的工具，不在启动时批量改写历史。

## 5. 写入方式与故障语义

1. **模块记录亲自验证的事实。** 统一写入器负责Schema、脱敏、关联和持久化；路由/中间件提供访问概况，AI、权限、编排和银行模块分别提供自身阶段，不能从HTTP状态推导业务结论。
2. **关键变更与结果事件同事务。** 银行资金/持仓/订单变化和对应审计一起提交；授权、确认、失败计数、状态推进等在各自状态事务内写事件。现有旧审计与新事件适配写入也同事务，任一失败则该事务不提交。
3. **执行开始先留痕。** 在关键变更或外部提交前，持久化已受理/准备提交事件。已有Outbox、受理和原操作号恢复机制继续使用。状态变化与审计完成后，才推进下一执行阶段。
4. **失败记录不随业务回滚丢失。** 尚未提交的变更先回滚并释放锁，再在独立审计事务写失败/拒绝事件；如失败计数等本身需要提交，则与其真实状态共同提交。不能在持有SQLite写锁时另开会话写日志，避免自锁。
5. **跨事务明确边界。** 一个事务失败不抹去先前已提交的事实；批量部分成功逐笔记录。银行已提交而响应丢失时写 `unknown`，后续按原操作号查询并追加核对结果。
6. **审计故障分层处理。** 关键变更在必需审计写不入时阻止提交，返回可识别的审计不可用错误；已提交交易的访问收尾日志失败不得把交易改成“未执行”。普通读取及失败事件可退到配置的受限追加文件，后续按事件ID幂等补录，并暴露审计降级状态。数据库和备用存储均不可用时明确报告不可记录，不宣称零丢失。
7. **崩溃恢复保留不确定性。** 只有开始记录而没有结束记录的执行标为待核对；有操作号的进入既有核对流程。没有证据时不自动补写成功/失败，不重新生成操作号扣款。

不增加消息队列或独立日志集群。追加文件仅是故障备用，不能代替关键账务的事务审计。

备用文件置于专用持久化目录，目录/文件权限分别限制为0700/0600，禁止放入静态资源目录或版本库；事件与数据库使用相同脱敏和Schema。设置单事件大小及磁盘预算，轮转后保留未补录段，补录完成才允许按配置归档。多进程追加要有进程间写入保护；达到容量上限视为备用不可用，不能覆盖未补录记录。补录以原事件ID去重，保留原发生时间和补录时间。

汇总状态由服务端事实投影产生：请求成功建立草稿显示“待确认”，不显示交易成功；中间工具失败后恢复成功保留该失败步骤，最终状态按实际业务终态确定；批量执行分别显示逐笔结果与整批部分成功。旧记录中的 `delegated` 权限及 `simulated` 结果保留原义，资料不足时标为未知，不默认转成绿色或成功。

## 6. 请求、AI与后台接入

- 使用适配流式响应的ASGI审计层，覆盖请求异常、响应发送和客户端断开；不全量读取/缓存请求体和响应体，不缓存SSE文本，避免破坏流式行为。
- 外部传入的关联标识只作为不可信引用；身份来自认证上下文。内部trace传播仅在内部凭据校验通过后采用，关联标识不授予权限。
- 在HTTP银行适配器、理财银行适配器和本地调用实现中保持相同关联语义。进程内上下文便利工具不能作为重启后恢复的唯一来源。
- NOVA记录：路由结果、结构化Goal Plan及依赖、离线/模型模式、模型/工具Schema版本、允许工具集合、工具开始与结束、参数校验、证据依据、安全阻断和最终回答的依据引用。账单、转账、理财等独立AI入口也接入，防止只覆盖统一聊天入口。
- 普通聊天和流式聊天复用同一事件逻辑；SSE的 `done/error`、HTTP传输完成及银行结果分别记录。断开时停止后续工作，但已提交事实和未知提交保留原状态。
- 调度器和理财worker每次执行建立系统上下文，关联原任务/操作/授权和attempt，记录触发、跳过原因、失败、重试与核对；进程重启仍可关联。
- 任务压缩、会话删除和演示清理前写入必要计划/节点/授权摘要；保留审计对象关联。新审计无普通更新/删除API，纠正通过追加更正事件完成。

## 7. 隐私与访问边界

- 按事件类型使用字段白名单，并对嵌套结构做二次过滤。禁止记录密码、JWT/内部Token、API密钥、验证码、TOTP密钥/二维码及完整银行卡号/手机号。
- 登录失败等无法确定用户的事件只保存结果、受控的标识摘要和必要访问信息，不从未经验证Token提取可信身份。
- 备注、聊天、商户说明、日历正文、上传文件和模型原始响应不直接复制到审计；按场景保存必要结构化事实、脱敏摘要和受控来源引用。低熵敏感内容如需关联摘要使用服务端带密钥摘要，不能以普通哈希充当脱敏。
- 关键版本快照保留足够核对的金额、币种、产品、费用和规则信息，不能仅存一个会随草稿删除而失效的引用；敏感身份信息仍使用内部对象ID和受控访问。
- 第一版页面/接口限本人数据，不新增全局管理员浏览权限。现有人工处理权限不自动获得全库审计权限；操作者与归属用户分别记录，后续如需审计员角色另行设计。
- trace、对象ID和游标均不能绕过用户隔离。查询与导出本身记录访问事件，但审计写入器不递归触发审计。
- 默认保留审计，无普通自动清理；本方案不预设法定保存年限。应用追加写入与删除路径保护不等于数据库管理员无法篡改，外部存证/不可变归档另行建设。

## 8. 查询与页面

拟增加：

- `GET /api/v1/audit/events`：按时间、业务、操作、结果、权限和业务对象筛选；服务端用户隔离、游标分页及单页上限。
- `GET /api/v1/audit/traces/{trace_id}`：单次入口执行及子步骤。
- `GET /api/v1/audit/objects/{object_type}/{object_id}`：按领域消歧，聚合该对象跨请求的完整生命周期、关联计划版本和回执。
- `GET /api/v1/audit/export`：复用本人过滤条件，限定时间跨度/条数的脱敏JSON导出，记录导出动作。

前端加入“操作记录”入口：列表展示时间、动作、结果和操作者；详情展示“请求—计划—校验—确认/验证—执行—结果”的时间线及必要证据。支持按任务/交易查看相关记录，区分待确认、处理中、已成功、失败、取消、阻断和待核对。权限和业务结果分别展示，历史资料不足明确标识。

普通页面不展示模型提示词、数据库细节或原始堆栈；必要的技术ID放在可展开详情中。加载、无数据、查询失败和审计降级有明确状态。

## 10. 验收清单

1. 每个在范围内的入口/关键服务均有覆盖映射，新增未分类路由使检查失败；直接服务调用和后台入口同样有业务审计。
2. 黄色转账、红色MFA转账、改金额导致旧确认失效、定时执行、付款退款及原号恢复能串起完整版本、规则、授权与银行结果。
3. 理财整份计划确认和一次MFA能关联逐笔执行；部分成功、赎回后申购依赖、参数变更、暂停/接管与清理后仍可还原链路。
4. 卡片、订阅、店铺及其他数据变更同时覆盖成功、拒绝、取消、过期、幂等重放和异常路径；绿色敏感查询有访问依据。
5. 注入阻断、无依据参数、未知/未允许工具、模型超时、连续重复熔断均留下明确事件，且没有伪造确认或成交结论。
6. 注入审计写入失败：资金/持仓/订单等对应变更不提交；业务回滚后的拒绝日志仍保留。已提交后访问收尾失败，查询原号仍返回真实结果。
7. 同一业务提交多次只产生一次业务效果与一次提交事实；每次访问/重试尝试可见；补录重放不重复生成同一事件。审计新增记录不能破坏旧表计数、风控及幂等语义。
8. 流式200后工具失败、客户端断开、银行超时已成交、进程中断后重启核对均正确区分传输和业务结果；没有结束事件时不冒充完成。
9. 删除聊天、压缩节点、演示清理后审计仍在且对象可追踪；历史无法补齐的阶段明确标记，不推造证据。
10. 对所有事件字段、嵌套值、异常及备用日志做敏感数据检查；跨用户trace/对象ID/游标/导出访问失败，响应不泄露其他用户信息。
11. 备用日志的权限、磁盘不可写、轮转/保留边界和幂等补录可验证；数据库和备用均失败时降级可见且关键变更停止。
12. SQLite与专用PostgreSQL库验证迁移、回滚与并发；前端验证筛选、分页、时间线、未知状态、空态及构建。没有PostgreSQL测试环境时明确记录未验证项，不把SQLite通过等同全部通过。

先做审计专项和受影响业务回归，再按项目要求运行完整离线后端测试及前端构建。真实模型联调另列为可选证据，不作为默认测试隐式联网。

## 11. 自审与已落实的方案修订

| 自审发现 | 已修订的设计 |
|---|---|
| 只增强HTTP日志无法解释决策，且后台调用会漏记 | 各模块记录实际事实；HTTP仅做访问概况；worker及独立AI入口接入 |
| 直接改变旧 `decision_chain` 结构或动作名会影响现有消费者 | 新结构化表；旧模型/风控语义保留，同事务适配，来源去重 |
| 把聊天会话、请求幂等键和操作号当一个标识会串错多任务 | 明确服务端请求/trace、业务幂等键和多对象关联；按对象聚合跨请求生命周期 |
| 失败事件跟随业务回滚丢失；另开连接可能引发SQLite锁冲突 | 明确事务边界和释放锁后的失败写入；有持久状态的失败与其状态同事务 |
| 在提交后发现日志失败并返回“交易失败”可能诱发重复扣款 | 提交事实同事务；收尾降级与交易结果分离；未知提交使用原号核对 |
| SSE响应开始即200不能代表业务完成；断开也不能代表交易取消 | 单独记录传输、助手终态和银行结果，并覆盖取消及恢复 |
| 任务节点、草稿引用会被清理，旧演示清理还删除审计 | 持久化必要版本快照；保留旧审计；新表无业务级联删除，清理本身留痕 |
| 全量存工具结果/对话会复制敏感信息，仅普通哈希也不安全 | 按类型白名单、嵌套过滤、必要事实与受控引用；敏感关联采用带密钥摘要 |
| 单写“完整、不可篡改、零丢失”会超出当前项目能力 | 明确历史缺口、双存储同时失败和应用追加写入的实际边界 |
| 只提供日志接口难以演示和验收 | 将本人操作记录页面、对象时间线和受控导出纳入同一次交付 |
| 二次复核：备用文件轮转可能覆盖未补录事件，多进程追加可能破坏记录 | 明确权限、持久目录、容量边界、跨进程保护、保留未补录段与原ID补录规则 |
| 二次复核：将草稿生成、模型成功回答或中间工具失败直接作为交易终态会误导 | 按可信业务事实生成汇总状态，区分待确认/部分成功，保留旧特殊值与未知状态 |

## 12. 已确认的范围

按上述完整方案实施：所有列明关键操作、本人操作记录页面及脱敏导出、旧记录兼容、新审计独立保留；复用现有数据库，不引入外部日志平台。全局审计员角色、外部不可变存证和法规保存期限不在本次新增范围。

用户确认后已开始实现。开发与验收使用隔离数据库；现有运行中的银行账本和部署保持原状。
